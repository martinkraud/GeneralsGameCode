## Finding

The README badge reports **GitHub milestone completion**, not a compiler/runtime
certification. [Milestone 5](https://github.com/TheSuperHackers/GeneralsGameCode/milestone/5?closed=1)
is titled x64 support and describes work towards x64 builds. Its displayed state
is 0 open and 3 closed items. One closed item is abandoned:

| Item | Displayed disposition |
|---|---|
| #784 OpenAL support | Closed, abandoned |
| #714 FFmpeg video playback | Merged/completed |
| #1563 64-bit-compatible Miles | Merged/completed |

Thus 100% counts closure, including abandonment. It proves neither that the
whole source is architecture-neutral nor that native Windows x64 Zero Hour
builds or runs. Individual issue bodies could not be fetched in this session;
the milestone list and local history provide the evidence above. Local commit
`8adf4852a` records #1563; later current loaders must take precedence over that
historical commit's title.

## Current local build evidence

| Evidence | Consequence |
|---|---|
| `CMakePresets.json` | Exposed Windows presets are Win32/VC6/i686, with no x64 preset |
| `.github/workflows/ci.yml` | Game matrix covers VC6 and win32 variants, no Windows x64 validation job |
| Top-level `CMakeLists.txt` | Includes DX8 SDK only for Windows with `CMAKE_SIZEOF_VOID_P == 4` |
| `Core/Libraries/Source/WWVegas/CMakeLists.txt:5` and `Core/GameEngine/CMakeLists.txt:1214` | Still link `d3d8lib`, whose SDK target is only created by that 32-bit dependency path |
| `WW3D2/CMakeLists.txt`, `dx8wrapper.h:46` | DX8 backend/wrapper still compiled; wrapper includes `d3d8.h` |
| `cmake/mingw.cmake:11` | Explicit fatal error for 64-bit MinGW; supports i686 only |
| `Dependencies/Bink/BinkLoader.cpp:22`, Miles equivalent | Actual DLL loading enabled only for `_WIN32 && !_WIN64`; other architectures fail load and use fallback return behavior |
| Build compiler metadata | Existing executable build is X86 with 4-byte pointers |

The fetched DX8 SDK CMake file under `build/win32/_deps/dx8-src` links legacy
Direct3D/D3DX8 libraries and defines BUILD_WITH_D3D8. Omitting its include is not
an alternative renderer selection. Merely passing `-A x64`, changing the
developer shell or adding a preset does not satisfy those dependencies.

**Conclusion:** this checkout has no supported, evidenced native Windows x64
Zero Hour build procedure. The current dependency graph does not supply a
complete x64 rendering/runtime route. Do not describe this as a preset-only
omission or as an already completed source port.

**UNKNOWN:** an exhaustive compiler-error inventory, whether some isolated
libraries/tests compile x64, and the complete amount of remaining port work.
No x64 configure/build was attempted, and this report does not claim a measured
failure log or claim that no conceivable external setup could compile it.

## Why other x64 reports exist

The upstream [build guide index](https://github.com/TheSuperHackers/GeneralsGameCode/wiki/build_guides)
places an MSVC x64 **Generals-only** route under community forks. The
[specific guide](https://github.com/TheSuperHackers/GeneralsGameCode/wiki/build_with_msvc22_x64_jmarshall2323)
explicitly refers to another author's fork with different code. It is not a
supported procedure for Zero Hour in this checkout.

## Remaining work categories, not an implementation plan for this session

1. Establish an architecture-capable graphics/dependency route and target graph;
   audit the legacy Direct3D/D3DX boundary rather than assuming headers suffice.
2. Provide functioning native audio/video alternatives or explicitly documented
   feature limitations. Current Bink/Miles fallback stubs do not provide playback.
3. Audit pointer widths/casts, Windows API storage, allocation/alignment, ABI,
   third-party code, architecture-guarded intrinsics/assembly and tools. Search
   hits alone do not prove an active defect: several adapters are VC6-only.
4. Audit snapshot/wire/file field widths, padding and ordering; compare CRCs
   and floating-point behavior with x86 and retail baselines.
5. Add focused x64 configure/build/runtime/CI verification only after a separate
   approved design. Preserve x86 as the known baseline.

No files were modified to investigate x64, and no port was started. Architecture
work is a separate compatibility project, not a prerequisite to profiling the
current engine or testing its existing render-rate features.
