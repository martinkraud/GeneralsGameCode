# Performance

This page explains what the MKRaudstein performance work measures, how, what it achieved and what it does **not** show. The detailed root-cause write-ups are in
[`findings/PERFORMANCE_FINDINGS.md`](findings/PERFORMANCE_FINDINGS.md); the per-milestone engineering records are `modernization/X64_38_CPU_SCALABILITY.md` ... `X64_42_SIMULATION_TAIL_OPTIMIZATION.md`.

## 1. What is being optimised (and what is not)

The goal is a **stable authoritative simulation** in large battles, not a high render frame rate.

* Original **Normal** game speed is **30 logic ticks per second** in both Generals and Zero Hour (proven from the source and the retail data in
  [`modernization/RETAIL_GAME_SPEED_AUDIT.md`](modernization/RETAIL_GAME_SPEED_AUDIT.md)). Each tick has a budget of **33.333 ms**.
* In this fork the simulation cadence is decoupled from rendering: raising the render FPS cap does **not** make the game run faster. Render pacing, interpolation and Render Scale are separate topics;
  this page is about the simulation thread.
* The average tick of even a very large AI battle is about 1 ms (3 % of the budget). What hurts is the **tail**: one 80-200 ms tick is a visible hitch in single player and a stall for every peer in
  multiplayer. The success criteria are therefore percentiles, the number of ticks over the budget, derived deadline misses and accumulated backlog - not the mean.
* Nothing here changes gameplay: every optimisation was built to give bit-identical simulation results, and each keeps the original algorithm selectable (see the findings).
* A future user-visible Game Speed setting is **design only** ([`modernization/GAME_SPEED_DESIGN.md`](modernization/GAME_SPEED_DESIGN.md)); Normal stays exactly 30 TPS.

## 2. Methodology

**Workload.** A replay with one idle human and seven Brutal computer players is a self-playing eight-player battle: the replay stores only the setup and the human's commands, the AI slots are simulated
by the engine. It is deterministic, repeatable, headless (no window, GPU, audio or input) and contains no proprietary content. The *heavy benchmark* is: map **Twilight Flame**, 7 Brutal AI
(USA/China/GLA cycled), free-for-all, seed 20 260, **72 000 ticks = 40 game minutes at 30 TPS**. It is generated by `scripts/performance/New-SimulationBenchmarkReplay.py` and run with
`generalsv.exe -headless -replay bench.rep` and `GENERALS_SIM_BENCH=<output base>` (`scripts/performance/Invoke-SimulationBenchmark.ps1` wraps repeated runs).
The first `GameLogic::update` (map start, 270-470 ms) is excluded and reported separately.

**Determinism fingerprint.** FNV-1a over `{logic frame, GameLogic::getCRC(), object count}` every 30 frames (2 400 checkpoints). The value for this benchmark is **`74F2CB528BED42ED`** and it was identical
in every run of every build and every optimised/legacy switch from X64.38 to X64.42, i.e. the optimisations did not change the simulation. A matching fingerprint is necessary but not sufficient evidence
(the state CRC does not contain everything, e.g. player money - see [`findings/REPLAY_DETERMINISM_FINDINGS.md`](findings/REPLAY_DETERMINISM_FINDINGS.md)); each optimisation therefore also has a local oracle that compares the actual intermediate data.

**A/B design.** Where possible the comparison is *the same executable* with an environment switch that selects the original code path, runs alternate A,B,A,B... with nothing else running, and the mean (and the
individual runs) are reported. The switches: `GENERALS_ZONE_LEGACY`, `GENERALS_PATH_LEGACY`, `GENERALS_LINE_LEGACY`, `GENERALS_NORMAL_LOG_FLUSH`.

**Attribution.** `PERFORMANCE_PROFILE_SCOPE` phases (exclusive times; nested scopes are subtracted from the parent). Trace modes (`GENERALS_SIM_PATHS`, `GENERALS_SIM_SCRIPTS`) add clock reads and are used for
attribution only, never for before/after timing.

## 3. Terminology

| term | meaning |
|---|---|
| p95 / p99 / p99.9 | nearest-rank percentile of the 72 000 whole-tick durations |
| ticks > 33.333 ms | ticks that took longer than the Normal-speed budget (also 16.67, 25, 50, 66.67, 100 ms) |
| slowest 1 % | the 720 slowest ticks; "share" is a phase's part of their summed time |
| derived missed deadlines, catch-up ticks, backlog | **a model, not a paced run**: ticks are assumed to run back to back as they become due, a tick that finishes after `slot start + 33.333 ms` misses its deadline, a tick that starts late is a catch-up tick, backlog is the accumulated lateness. It turns measured durations into real-time consequences; it does not simulate a frame pacer |
| fingerprint | see above |

## 4. Results, one direct comparison per milestone

Every table is a same-executable alternating A/B unless stated. Numbers are means of the stated number of runs; "worst" is the mean of the per-run worst tick. Different milestones were measured in
different sessions with harness versions of their time, so **milestone tables are not one continuous series** (the absolute baselines differ by session; see section 5 for the end-to-end comparison).

### X64.43 - exhaustive failing path searches: characterised, not optimised

No production change. The remaining tail (A* searches that exhaust the open list: 580 per heavy run, 6-7 above 20 ms) was explained by an off-by-default read-only diagnostic: the searches explore the whole connected
pocket of the requester (~22 000 cells) because stationary non-idle allied units and uncrushable enemy units seal a chokepoint, while the terrain and the zone data say the goal is reachable. Repeats are too rare and the pathfinder
cell state changes too much (2 of 120 repeats saw no change) for any exact failure reuse. Decision: no justified optimization. Record: [`modernization/X64_43_FAILING_PATH_INVESTIGATION.md`](modernization/X64_43_FAILING_PATH_INVESTIGATION.md).

## 5. End-to-end: all original code paths vs the current defaults (same executable)

All four legacy switches together (original ZoneCalc, original open-list walk, original line walk, per-record log flush) against the defaults, **the same executable built from the current HEAD**, alternating, 4 rounds each,
fingerprint `74F2CB528BED42ED` in all 8 runs. This is the one comparison that spans the whole series without mixing sessions or harness versions. The legacy arm is the original algorithms with the current
(inert) instrumentation, not the pre-X64.38 binary.

| whole tick | all legacy | defaults |
|---|---|---|
| mean / median | 1.365 / 0.711 ms | 0.945 / 0.708 ms |
| p95 / **p99** / **p99.9** | 2.59 / **22.84** / **49.66** ms | 2.20 / **5.89** / **10.43** ms |
| worst (mean of runs; per run) | 288.0 (302 / 308 / 274 / 267) ms | 85.0 (84.7 / 92.5 / 82.1 / 80.9) ms |
| ticks > 16.67 / 25 ms | 856 / 529 | 34.0 / 7.2 |
| **ticks > 33.3 / 50 / 66.7 ms** | **204 / 71.5 / 51.0** | **4.5 / 2.2 / 2.0** |
| derived missed deadlines | 414 | 8.0 |
| longest catch-up run | 125 ticks | 3.2 ticks |
| **max derived backlog** | **2 994 ms** | **51.7 ms** |
| `path_search` total / worst | 20 324 / 260 ms | 4 589 / 78 ms |
| `logic_scripts` worst | 86.6 ms | 3.5 ms |

Per-run defaults: p99 5.77 / 6.30 / 5.71 / 5.78 ms, ticks > 33.3 ms 4 / 6 / 4 / 4, derived missed 7 / 11 / 7 / 7. One default run (the second) was slower than the others (mean 1.04 ms, p99.9 14.1 ms), which is why runs are shown.

Reading: on this workload and machine ticks over the 33.3 ms budget fell about 45x (204 -> 4.5), derived missed deadlines about 52x, derived backlog about 58x, and p99 about 3.9x, while the **median is unchanged** and the mean
improved by 31 %: the work removed was the rare expensive ticks, not the typical one. This is *not* a statement that "the game is N % faster".

## 6. Current profile (after X64.42; slowest 1 % of ticks, run B1 of the X64.42 A/B)

| phase | share of the slowest 1 % |
|---|---|
| `path_search` | 39.6 % |
| `zone_flatten` / `zone_hierarchy` / `zone_label` / `zone_relabel` | 12.1 % / 6.7 % / 5.7 % / 4.5 % |
| `ai_object_base_update` | 7.5 % |
| `path_request_entries` | 5.1 % |
| `object_update_loops` | 3.5 % |
| `logic_scripts` | < 2 % |

Cumulative CPU over the whole run: `ai_object_base_update` 37.7 % (many cheap calls, individual maximum under 5 ms - throughput, not tail), `object_update_loops` 17.6 %, `logic_scripts` 8.9 %, `logic_partition` 7.1 %,
`path_search` 6.9 %.

Known remaining areas: (1) rare exhaustive *failing* path searches (≈104 000 pops over ≈21 000 distinct cells and ≈6 M line-walk callbacks, 70-80 ms, a handful per 72 000 ticks; characterised in X64.43: sealed by stationary units, no exact shortcut found); (2) ZoneCalc recalculations that
coincide with other work (≈5.6 ms each, 386 per run); (3) `ai_object_base_update` throughput; (4) a one-time frame-0 AI supply-source setup of 15-120 ms depending on the map, which is a **map-load cost, not a recurring
gameplay tick**. A few isolated 30-60 ms values in a 16-map table did not reproduce on re-run; they are treated as noise and are not claimed as engine problems.

## 7. Limits of these results

* One development machine (Intel Core Ultra 5 125U, 14 logical processors, Windows 11), one build configuration (x64 Release), one benchmark map/composition, AI against AI. A 1-human-vs-AI game, other maps
  (16 maps were checked for determinism and exactness, not re-timed against the original code), other CPUs, drives, background load, other Windows power modes may differ. Do not generalise the numbers.
* The deadline/backlog figures are derived from measured durations; they are not a paced run on a clock.
* Run-to-run noise is visible (see the per-run values); a single worst tick can be an operating-system stall.
* The numbers describe the simulation thread only. Rendering, audio and I/O costs are measured elsewhere (renderer instrumentation, `X64_35_*` documents).
* No multiplayer, lockstep or Zero Hour benchmark exists; no threads are used by the simulation (the serial algorithmic work came first by decision).

## 8. Reproduce

```
python scripts/performance/New-SimulationBenchmarkReplay.py --template "<any replay recorded by this build>.rep" --out bench.rep --map "Twilight Flame" --map-size 402471 --ai 7 --level H --minutes 40 --seed 20260
set GENERALS_SIM_BENCH=out\run1
set GENERALS_SIM_IGNORE_CRC=1
generalsv.exe -headless -replay bench.rep
```

Run from the game directory (the engine finds its data relative to the executable). Use `GENERALS_ZONE_LEGACY=1`, `GENERALS_PATH_LEGACY=1`, `GENERALS_LINE_LEGACY=1`, `GENERALS_NORMAL_LOG_FLUSH=1` for the original behaviour,
and the `*_VERIFY` switches to compare an optimisation against the original on every call. A proprietary-asset-free benchmark requires the game's own data and an executable built from this repository.

## 9. Has the serial CPU optimization phase reached diminishing returns?

After X64.43: yes, for this workload. The heavy 8-player benchmark misses the 33.333 ms budget about 8 times in 72 000 ticks with a 0.7 ms median; the remaining tail is workload-specific (large armies sealing chokepoints) and has no cheap exact
shortcut; `ai_object_base_update` is throughput, not tail; further gains would need parallelism or behaviour changes. The proposed next measurement is a real-game scalability benchmark (design in the X64.43 document), not another optimization.
